# syntax

Language detection and parse trees. No drawing (highlighting comes in 8b).

- `language.rs` — `Language` (`PlainText`, `C`, `Cpp`, `Python`): `id()` (`plaintext`, `c`, `cpp`, `python`: VS Code's ids, which LSP's `languageId` and `.workspace` associations use), `name()` (status bar), `grammar()` (tree-sitter `Language`), `highlight_queries()` (C++'s `highlights.scm` extends C's: both, C's first). `Associations` compiles `[files] associations` (glob → id; a glob with `/` matches the path relative to the root, else the file name; bad globs / unknown ids are returned as errors). `detect(path, root, first_line, associations)`: associations, then name / extension (VS Code's lists; `.h` is C++ as in VS Code; `SConstruct`/`SConscript`/`*.scons` are Python), then a `python*`/`pypy*` shebang (`env`, its options and `VAR=x` skipped). Pure: no I/O.
- `mod.rs` — `Syntax` (one per `Buffer`): `language()`, `set_language` (a change drops the tree), `tree()` (`Some` only when current), `edit(changes, old, new)` (from `Buffer::apply`: each change → an `InputEdit` in the coordinates left by the earlier ones, positions via `pos::ts_point`; a set over `COALESCE_AT` (256) changes → one edit spanning them, or, spanning over `INLINE_BYTES`, back to `Wanted` with the old tree kept in `discard` for the next `ParseJob` to free off-thread), `update(rope, max_bytes)` (called by `App::sync_syntax`) and `parsed(Parsed)`.
  - States: `Off` (no grammar), `TooLarge` (over `max_bytes`, 0 = never), `Wanted` (needs a full parse), `Parsing` (a background parse in flight: edits made meanwhile queue up and are applied to its result, up to `MAX_QUEUED` (4096) before it restarts; replacing the state drops `Cancel`, which stops the parse), `Ready` (tree + edits since it was parsed).
  - `update`: small pending edits (≤ `INLINE_EDITS` changes touching ≤ `INLINE_BYTES`) are re-parsed incrementally on the UI thread, stopping after `INLINE_TIME` (12 ms); anything else (first parse, big edits, a re-parse that ran out of time) returns a `ParseJob` (rope snapshot + the edited old tree) for `spawn_blocking`; `ParseJob::run` is blocking and returns `Parsed` (dropped by `parsed` unless its generation is current; a tree finished after its cancel is freed in the job, not on the UI thread).
  - `parse` reads the rope chunk by chunk (`pos::chunk_from`, no copy). A stop (deadline or cancel) is checked in both the progress callback and the read callback (one lexer step can scan to the end of the file, e.g. an unterminated `/*`); once stopped it reports end of text and the result is dropped.
- Logging under `red::syntax`: parse times at debug, `slow parse` warning over 500 ms.
- Tests (`tests.rs`) drive `Syntax` through a `Buffer` without the app: `update` → `job.run()` → `parsed`; the random-edit test compares the incrementally kept tree with a fresh parse (S-expression and every node's range and positions); `input_edits_match_a_reference` checks the `InputEdit`s against ones computed by applying each change to a string. tree-sitter's error recovery can differ between incremental and fresh parses after many broken edits, so it runs a fixed number of seeded steps.
