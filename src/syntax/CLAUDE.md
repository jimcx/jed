# syntax

Language detection, parse trees and highlight spans. No drawing (the editor draws the spans).

- `language.rs` — `Language` (`PlainText`, `C`, `Cpp`, `ObjC`, `ObjCpp`, `Swift`, `Python`, `Rust`, `Markdown`, `Yaml`, `Json`, `Jsonc`, `Xml`, `Toml`, `ShellScript`, `CMake`, `Makefile`, `Dockerfile`, `GitCommit`, `GitRebase`, and `Plugin(PluginId)` for a syntax plugin): `Language::BUILT_IN` (the compiled-in array) and `all()` (those plus the registered plugins); `Language::scope_of(kind)` (a plugin's kind lists, then `scope_of`); `id()` (VS Code's ids: `plaintext`, `c`, `cpp`, `objective-c`, `objective-cpp`, `swift`, `python`, `rust`, `markdown`, `yaml`, `json`, `jsonc`, `xml`, `toml`, `shellscript`, `cmake`, `makefile`, `dockerfile`, `git-commit`, `git-rebase`, which LSP's `languageId` and `.workspace` associations use), `name()` (status bar, VS Code's: "JSON with Comments", "Shell Script", …), `grammar()` (tree-sitter `Language`; crates `tree-sitter-{c,cpp,objc,swift,python,rust,md,yaml,json,xml,toml-ng,bash,cmake,make,containerfile,gitcommit}`, all on `tree-sitter-language` (tree-sitter-objc is MIT, ~28 MB of `parser.c`; Objective-C++ uses it too, as it parsed `.mm` samples with fewer errors than tree-sitter-cpp; tree-sitter-swift 0.7.4 is MIT, ~23 MB of `parser.c` + `scanner.c`); Markdown is the block grammar only (`tree_sitter_md::LANGUAGE`), so inline emphasis / code spans / links aren't parsed; JSON and JSONC share tree-sitter-json, which accepts comments), `highlight_queries()` (the grammar's `highlights.scm`, C++'s and Objective-C's after C's, then jed's additions in `queries/<lang>.scm`: control keywords, built-in types, parameters, `self`, YAML keys as tags, XML tag punctuation, … for Dark+'s colours; for the same node a later pattern wins, so additions go last; Rust starts with an inline `(identifier) @variable`, and `queries/swift.scm` (the grammar's query plus control flow / `import` / `#if` as `keyword.control`, `@attributes` as keywords, members as properties, shebang a comment), and `queries/objc.scm` with the same (the grammar's query paints every identifier a property: its `#has-ancestor?` isn't evaluated) before restating C's upper-case constants, `YES` / `NO` / `nil`, types / methods / parameters; CMake (`#lua-match?`, which tree-sitter ignores) and TOML (captures whole pairs) use only jed's query). `Associations` compiles `[files] associations` (glob → id; a glob with `/` matches the path relative to the root, else the file name; bad globs / unknown ids are returned as errors). `detect_path(path, root, associations)` (associations, then the name: `None` = the shebang decides) and `detect_shebang(first_line)` (else plain text) are its two halves, for a diff tab whose text is read off-thread. `detect(path, root, first_line, associations)`: associations, then `by_name` (exact names first: `Makefile` / `GNUmakefile`, `CMakeLists.txt`, `Dockerfile` / `Containerfile`, `Cargo.lock` / `Pipfile` / `poetry.lock` / `uv.lock` and jed's `.workspace` (TOML), `tsconfig.json` / `.eslintrc` / … (JSONC), `.clang-format` (YAML), shell dotfiles `.bashrc` / `.zshrc` / `.profile` / … and `PKGBUILD`; then `Dockerfile.*` / `Containerfile.*`, `tsconfig.*.json`, `.vscode/*.json` (JSONC); multi-dot suffixes `.js.map` / `.csproj.user`; then the extension, case-insensitive, VS Code's lists; a dotfile's name isn't an extension (`.c` is plain text); `.m` is Objective-C and `.mm` Objective-C++; `.swift` is Swift; `.h` is C++ as in VS Code (not sniffed for Objective-C: detection of a path doesn't read the text); `SConstruct`/`SConscript`/`*.scons` are Python), then the shebang's program (`env`, its options and `VAR=x` skipped; a trailing version allowed): `python*`/`pypy*` → Python, `sh`/`bash`/`zsh`/`ksh`/`dash`/`ash`/`mksh`/`yash`/`csh`/`tcsh`/… → shell, `make` → Makefile, `swift` → Swift. `GitCommit` ("Git Commit Message"): `COMMIT_EDITMSG` / `MERGE_MSG` / `SQUASH_MSG` / `TAG_EDITMSG` / `EDIT_DESCRIPTION` / `NOTES_EDITMSG`; `GitRebase` ("Git Rebase Message", `git-rebase-todo`) has no grammar or query (uncoloured, `#` comments). tree-sitter-gitcommit only builds `generated_comment` (branch, change kinds, paths) after git's real "Please enter the commit message…" header; its `comment` nodes are plain (`queries/git-commit.scm` keeps a `title` in one, `# Conflicts:`, a comment; `BREAKING CHANGE:` a keyword). Pure: no I/O.
- `plugin.rs` — syntax plugins' manifests and registry (`~/.config/jed/languages/<id>/language.toml`): `parse(text, file)` (lenient: unknown keys / bad values go to the returned errors, the rest applies; `None` without a usable `id`), `load_dir` (blocking; a directory name must equal `id`), `register(Manifest)` (rejects built-in and duplicate ids; leaks a `Plugin` with its `'static` `LanguageConfig`, filling gaps with `config(…)`'s defaults) and `load_and_register` (called by `main` only for the user's config dir, errors joining `app.set_keymap`'s). `PluginId` (`get` / `find` / `all`) indexes the append-only global registry, so tests register unique ids, never assume it is empty, and claim no extension, file name or shebang another test detects (one that wins, like `.h`, would change it). `PluginId::load` (blocking; called by `App::load_grammars` for each of `app.syntax_plugins` (`main` sets the whole registry; tests their own) after `build::build` when `Plugin::buildable()` (`src/parser.c`), else as is from a prebuilt `parser.so` / `parser.dylib` (`Plugin::loadable()`)) opens the library with `libloading`, takes `symbol`, wraps it with `LanguageFn::from_raw`, checks `abi_version()` against tree-sitter's `MIN_COMPATIBLE_LANGUAGE_VERSION..=LANGUAGE_VERSION` before any parse, compiles `queries/highlights.scm` + `queries/jed.scm` (a missing file is empty; a bad query reports its file, line and column) and installs the query then the grammar in the `Plugin`'s `OnceLock`s (`Language::grammar()` and `highlight::query` read them; no grammar until then, so files open uncoloured with `Syntax` `Off`, and `Syntax::grammar_installed` moves them to `Wanted`). The library is leaked (`mem::forget`) once loaded; a failure closes it, is returned as a string (only successes are kept, so the next `load` tries again) and leaves the language without a grammar. Concurrent loads open the same library, so the `set`s that win agree. `plugin::test_lib` (tests) builds the vendored `examples/languages/cmake/src` through `build::build` once per process (also an ABI 12 variant) and writes plugin directories; tests skip with a note without a compiler. Detection in `language.rs`: associations, `built_in_named` (exact names and name patterns), plugin `filenames`, plugin `extensions` (case-insensitive, multi-dot allowed, non-empty stem; beats built-in ones, so a plugin can claim `.h`), `built_in_extension` (suffixes, extensions), then shebangs (built-in programs, then plugins' `shebangs` by the same program rule). `examples/languages/cmake/language.toml` is the commented template; `queries/highlights.scm` beside it is a copy of `queries/cmake.scm` (`syntax_plugins_template_query_is_built_in`). `syntax_plugins_template_matches_built_in_cmake` keeps the manifest equal to the built-in CMake's config and detection, and `syntax_plugins_template_spans_match_built_in_cmake` builds the template (its manifest minus `[files]`, under a unique id) and compares its highlight spans with the built-in's.
- `build.rs` — building a plugin's grammar (blocking, app-free; `--check-language` shares it): `build(dir, &Toolchain, force) -> Build { outcome: NoSources | Fresh | Built | Failed(why), log }`. `Toolchain::from_env` = `$CC` else `cc`, `$CXX` else `c++` (passed in, so tests never set env vars). `src/parser.c` (+ `scanner.c`) compile in one `cc -shared -fPIC -O2 -I src` command (`-dynamiclib` on macOS); with a `scanner.cc`, `parser.c` and the scanner are compiled to objects (`cc -c`, `c++ -c`) and linked with `c++`. The library goes to a temp file in the plugin dir and is renamed over `LIBRARY` (never written in place: a loaded one stays valid). `build.toml` stamps `inputs` = SHA-256 over the `.c` / `.cc` / `.h` files in `src/` and `src/tree_sitter/` (names and contents), the compilers and their `--version` line, OS and arch; `Fresh` when it matches and the library exists (no file times); written only after a success, so a failure keeps the old library and stamp. `log` = `$ <command>` lines and the compiler's output (`up to date` for `Fresh`). Failure text: `` `cc` failed (exit status): <first error line> `` or `cannot run …`. The app runs it from `App::load_grammars` (see `app/syntax.rs`).
- `authoring.rs` — `jed --new-language <id>` / `--check-language <id> [--sample <file>]` (`main` prints the returned text and exits): `new_language(languages_dir, id)` writes the embedded template (`include_str!` of `examples/languages/cmake/language.toml`, with `id` / `name` / `symbol` / `[files]` filled in and CMake's comment and node kinds cleared; its line replacements are by prefix, so reword the template with care) plus empty `src/` and `queries/`, never over an existing directory or a built-in id; `check_language(languages_dir, id, sample, &Toolchain) -> (text, ok)` runs manifest (`plugin::parse` errors, with the key's line found by scanning the text within its table, comments skipped; a `pairs.…` error gets `pairs`'s line), build (`build::build`, its log shown), load and query (`PluginId::load`), then notes (captures with no theme key and the keys they could alias to, the comment / string node kinds `scope_of` sees) and the sample coloured by `Theme::ansi`. It registers the plugin, so it runs once per process. Tests use `test_lib` and unique ids.
- `config.rs` — `LanguageConfig` (`Language::config()`), VS Code's `language-configuration.json` data: `line_comment` (`//` for C/C++/Objective-C/Swift/Rust/JSONC, `#` for Python/YAML/TOML/shell/CMake/Makefile/Dockerfile; none for plain text, JSON, Markdown and XML: block comments only, which comment line doesn't do), `pairs` (`AutoPair { open, close, not_in_string, not_in_comment }`, single chars only: no `/*` / `/**` / `<!--` pairs), `brackets` (VS Code's `brackets`, single chars: auto-indent and bracket matching; `{}` `[]` `()` mostly, JSON `{}` `[]`, TOML `{}` `[]`, XML `<>` `{}` `()`), `tree_tokens` (false for Markdown: its block tree keeps a paragraph's text in one leaf, so brackets are read from the text, see `Syntax::token_tree`), `insert_spaces` (a language-specific default over the user's setting: `Some(false)` for Makefiles, VS Code's `[makefile]`; `edit::Settings::for_buffer` applies it, over any indentation guessed from the text), `surround` (C/C++/Rust also `<>`, Python and shell backticks, Markdown also `` ` `` `_` `*` `~` `$`), `close_before_quotes` / `close_before_brackets` (VS Code's `autoCloseBefore` defaults: none of the languages sets its own), `string_prefixes` (Python `r u f b`: VS Code's `f'`, `r"`, … pairs, `notIn` strings and comments). Swift is `C_LIKE` without the `'` pair. `notIn` per VS Code's files: C/C++/Objective-C(++) (one `C_LIKE` config; `@"` closes as `"` does) `'` not in strings or comments, `"` not in strings; Python `'` not in strings or comments, `"` and backtick not in strings; Rust only `"` among the quotes (lifetimes), not in strings; JSON / JSONC every pair not in strings, `"` and backtick not in comments either; YAML both quotes anywhere; XML `'` not in strings or comments, `"` not in strings; TOML, shell, CMake, Dockerfile quotes not in strings; git-commit `#`, brackets `[` `(` only (no quotes: apostrophes), git-rebase `#` only; Makefile as C; Markdown `<` not in strings, quotes don't auto-close. TOML and CMake have no VS Code built-in: Even Better TOML's and the CMake extension's data. Plain text = VS Code's built-in plaintext config: brackets auto-close, quotes don't; wraps in brackets, `<>`, quotes, backticks. Helpers: `is_pair_char`, `pair_opened_by`, `closes`, `brackets()`, `surround_for`, `closes_before(open, next)`; `is_quote`. A `const fn config(…)` builds the common case (default `autoCloseBefore`, tree tokens, user's indentation); `..config(…)` overrides the rest.
- `mod.rs` — `Syntax` (one per `Buffer`): `language()`, `scope_before(pos)` (`Scope::{Code, String, Comment}` of the char before `pos`: the smallest node holding it and its ancestors, each asked `scope_of(kind)`; `None` without a current tree — auto-close's `notIn`), `scope_of(kind)` (the one table of node kinds across the grammars: a kind containing `comment` (or XML's `Comment`) is a comment; one containing `string` (not Dockerfile's `unquoted_string`) or `char_literal`, YAML's quoted / block scalars, `heredoc_body`, CMake's quoted / bracket arguments, XML's `AttValue` / `EntityValue` / … is a string; `interpolation`, Swift `interpolated_expression` / `raw_str_interpolation` / `key_path_string_expression` and the `\(` leaf (a child of the string), shell `expansion` / `simple_expansion` / `command_substitution` and CMake's `variable_ref` are code again; else the parent's; also used by `indent.rs` for trailing comments and closers in strings), `set_language` (a change drops the tree), `tree()` (`Some` only when current), `token_tree()` (the current tree when `LanguageConfig::tree_tokens`: what bracket matching and auto-indent read brackets from; Markdown's is `None`, so they scan the text), `tokens()` (a `Tokens` walk over the `token_tree`), `edit(changes, old, new)` (from `Buffer::apply`: each change → an `InputEdit` in the coordinates left by the earlier ones, positions via `pos::ts_point`; a set over `COALESCE_AT` (256) changes → one edit spanning them, or, spanning over `INLINE_BYTES`, back to `Wanted` with the old tree kept in `discard` for the next `ParseJob` to free off-thread), `update(rope, max_bytes)` (called by `App::sync_syntax`) and `parsed(Parsed)`. `highlight_text(language, text)` (blocking): one full parse of a text no buffer holds and `highlight::compute` over all of it (a diff tab's sides; the caller applies the size limit).
  - States: `Off` (no grammar), `TooLarge` (over `max_bytes`, 0 = never), `Wanted` (needs a full parse), `Parsing` (a background parse in flight: edits made meanwhile queue up and are applied to its result, up to `MAX_QUEUED` (4096) before it restarts; replacing the state drops `Cancel`, which stops the parse), `Ready` (tree + edits since it was parsed).
  - `update`: small pending edits (≤ `INLINE_EDITS` changes touching ≤ `INLINE_BYTES`) are re-parsed incrementally on the UI thread, stopping after `INLINE_TIME` (8 ms: with the highlight query and the frame a key stays near 10 ms); anything else (first parse, big edits, a re-parse that ran out of time) returns a `ParseJob` (rope snapshot + the edited old tree) for `spawn_blocking`; `ParseJob::run` is blocking and returns `Parsed` (dropped by `parsed` unless its generation is current; a tree finished after its cancel is freed in the job, not on the UI thread).
  - `parse` reads the rope chunk by chunk (`pos::chunk_from`, no copy). A stop (deadline or cancel) is checked in both the progress callback and the read callback (one lexer step can scan to the end of the file, e.g. an unterminated `/*`); once stopped it reports end of text and the result is dropped.
- `highlight.rs` — `KEYS` (the theme keys a capture can map to; each is in `Theme::dark_plus`; besides the code token keys, `diff.*` / `overflow` / `invalid` (the git commit line pass), `markup.heading` / `markup.list` / `markup.quote` / `markup.raw` / `markup.link` for Markdown and `tag` / `tag.attribute` / `punctuation.tag` for XML (YAML keys are `tag`, Dark+'s `entity.name.tag.yaml`)), `ALIASES` (the grammars' own names for those: `boolean` → `constant.builtin`, `string.special.key` → `property`, `string.escape` → `escape`, `keyword.conditional` / `conditional` / `include` / … → `keyword.control`, `storageclass` → `keyword`, `namespace` → `type`, `method` → `function`, `parameter` → `variable.parameter`, Neovim's `text.title` / `text.literal` / `text.uri` / `text.reference` → markup keys), `highlight_for(capture)` (the dotted name, else its longest prefix, each in `KEYS` then `ALIASES`: `function.method` → `function`; none → uncoloured, and an uncoloured capture doesn't paint, so an earlier pattern's colour for the node stays), `Span { start, end, highlight }` (`ByteIdx` range; `Highlight::index()` indexes `KEYS`). Each language's query is compiled once (`OnceLock`; `warm` is called by `ParseJob::run`, so the UI thread never compiles it). `compute(language, tree, rope, start, end)`: a `QueryCursor` over the byte range (text predicates read the rope via `pos::bytes_in`), captures painted into a byte array (outer nodes first, inner over them; for the same node the later pattern wins), run-length encoded into sorted, non-overlapping spans clipped to the range (a block comment opened above the range colours its part). For `Language::GitCommit` a line pass (`git_commit_lines`) paints over the query's colours before encoding: the subject's text past 50 graphemes `overflow`, text on line 2 `invalid`, and below the `scissor` node (`git commit -v`) the diff by line kind (`diff.header` / `diff.hunk` / `diff.inserted` / `diff.deleted`, one `pos::line_bounds` per line of the range, so O(range)); `LanguageConfig::rulers` (`git-commit`: `[72]`) is that language's default `rulers` setting (`Settings::for_language`; a user's `rulers`, even `[]`, wins). The subject's 50 counts graphemes (a wide CJK char is one).
  - `Highlights` (inside `Syntax`, reached through `Syntax::spans(rope, lines)`): up to 4 cached `Region`s (a byte range + spans + the `tree_version` they came from). With a current tree: a region of that version covering the lines, else query the lines ± `MARGIN` (50) and cache it (older versions dropped). Bytes are capped so one query stays under ~7 ms (~0.3 ms per KB of dense C++): only `MAX_QUERY_BYTES` (16 KB) from the first requested line's start are coloured (a 1 MB minified line: just its start, as VS Code stops tokenizing long lines), and the margin is at most `MARGIN_BYTES` (4 KB) either side; a caller wanting more (the Minimap) asks in pieces. Without one (re-parse running): the newest region that covers or overlaps, mapped through every change set by `Syntax::map_highlights` (from `Buffer::apply`; span starts `Assoc::After`, ends `Before`, so text typed at a span's edge stays plain until the new tree; emptied spans dropped). Positions are only compared, never used to index the rope. `set_language` and going `TooLarge` clear the cache. `tree_version` is bumped whenever a new current tree is installed (inline re-parse, or a background result with no edits queued).
  - Tests (in `highlight.rs`): prefix and alias mapping, every language's query compiling with each capture name mapped to a key or listed as intentionally plain (`attribute`, `none`, `embedded`, `spell`, `markup` (XML text), `@_` predicate names, …), exact spans for a snippet per language (C / C++ / Objective-C / Swift / Python / Rust / Markdown / YAML / JSON / JSONC / XML / TOML / shell / CMake / Makefile / Dockerfile), `#match?` predicates (also on a node spanning rope chunks), a comment opened above the range, the cache (`highlight_queries_run()` counts misses: none when nothing changed; stale spans shifted by an insert; right after the re-parse), stale span edges, deleted spans, language change and the size limit dropping the cache, the long-line cap.
- `tokens.rs` — `Tokens`: a `TreeCursor` walk over the tree's leaves for positions asked in increasing order (each node stepped over once; an earlier position restarts from the root): `leaf_from(b)` (first leaf ending after `b`; zero-width missing leaves skipped), `leaf_at(b)` (the leaf holding `b`, `None` between tokens), `is_token(b, text)` (a bracket that isn't inside a string / comment: those are single leaves or content leaves), `node_at(b)` (the leaf holding `b`, else the innermost node with `b` in a gap between its children: Rust's `line_comment` / `block_comment` hold only their delimiters as leaves; what auto-indent asks `scope_of` about), `each_leaf(lo, hi, f)`. Avoids `descendant_for_byte_range` per position, which scans a node's children linearly (a root with 60k children).
- Logging under `jed::syntax`: parse times at debug, `slow parse` warning over 500 ms.
- Tests (`tests.rs`) drive `Syntax` through a `Buffer` without the app: `scopes_in_every_language` (string / comment / code positions per grammar), `scope_kinds`, `markdown_has_no_token_tree`; `update` → `job.run()` → `parsed`; the random-edit test compares the incrementally kept tree with a fresh parse (S-expression and every node's range and positions); `input_edits_match_a_reference` checks the `InputEdit`s against ones computed by applying each change to a string. tree-sitter's error recovery can differ between incremental and fresh parses after many broken edits, so it runs a fixed number of seeded steps.
- **Parse trees:** `buf.syntax.tree()` is `Some` only while the tree matches the text exactly (never a stale one); between an edit and the next `sync_syntax`, and while a background parse runs, it is `None`. Drawing never reads the tree: it asks `buf.syntax.spans(rope, lines)`, which keeps the last colours (mapped through the edits) until the new tree arrives. tree-sitter `Point`s come from `pos::ts_point` (rows count LF only, as tree-sitter does).
