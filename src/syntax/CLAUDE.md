# syntax

Language detection, parse trees and highlight spans. No drawing (the editor draws the spans).

- `language.rs` — `Language` (`PlainText`, `C`, `Cpp`, `Python`): `id()` (`plaintext`, `c`, `cpp`, `python`: VS Code's ids, which LSP's `languageId` and `.workspace` associations use), `name()` (status bar), `grammar()` (tree-sitter `Language`), `highlight_queries()` (the grammar's `highlights.scm`, C++'s after C's, then red's additions in `queries/{c,cpp,python}.scm`: control keywords, built-in types, parameters, `self`, … for Dark+'s colours; for the same node a later pattern wins, so additions go last). `Associations` compiles `[files] associations` (glob → id; a glob with `/` matches the path relative to the root, else the file name; bad globs / unknown ids are returned as errors). `detect(path, root, first_line, associations)`: associations, then name / extension (VS Code's lists; `.h` is C++ as in VS Code; `SConstruct`/`SConscript`/`*.scons` are Python), then a `python*`/`pypy*` shebang (`env`, its options and `VAR=x` skipped). Pure: no I/O.
- `config.rs` — `LanguageConfig` (`Language::config()`), VS Code's `language-configuration.json` data: `line_comment` (`//`, `#`, none for plain text), `pairs` (`AutoPair { open, close, not_in_string, not_in_comment }`, single chars only: no `/*` / `/**` pairs), `surround` (C/C++ also `<>`, Python also backticks), `close_before_quotes` / `close_before_brackets` (VS Code's `autoCloseBefore` defaults: none of the three languages sets its own), `string_prefixes` (Python `r u f b`: VS Code's `f'`, `r"`, … pairs, `notIn` strings and comments). C/C++: `'` not in strings or comments, `"` not in strings; Python: `'` not in strings or comments, `"` and backtick not in strings (VS Code's files). Plain text = VS Code's built-in plaintext config: brackets auto-close, quotes don't; wraps in brackets, `<>`, quotes, backticks. Helpers: `is_pair_char`, `pair_opened_by`, `closes`, `brackets()` (the non-quote pairs: auto-indent and bracket matching), `surround_for`, `closes_before(open, next)`; `is_quote`.
- `mod.rs` — `Syntax` (one per `Buffer`): `language()`, `scope_before(pos)` (`Scope::{Code, String, Comment}` of the char before `pos`: the smallest node holding it and its ancestors, `interpolation` counting as code; `None` without a current tree — auto-close's `notIn`), `set_language` (a change drops the tree), `tree()` (`Some` only when current), `tokens()` (a `Tokens` walk over the current tree), `edit(changes, old, new)` (from `Buffer::apply`: each change → an `InputEdit` in the coordinates left by the earlier ones, positions via `pos::ts_point`; a set over `COALESCE_AT` (256) changes → one edit spanning them, or, spanning over `INLINE_BYTES`, back to `Wanted` with the old tree kept in `discard` for the next `ParseJob` to free off-thread), `update(rope, max_bytes)` (called by `App::sync_syntax`) and `parsed(Parsed)`.
  - States: `Off` (no grammar), `TooLarge` (over `max_bytes`, 0 = never), `Wanted` (needs a full parse), `Parsing` (a background parse in flight: edits made meanwhile queue up and are applied to its result, up to `MAX_QUEUED` (4096) before it restarts; replacing the state drops `Cancel`, which stops the parse), `Ready` (tree + edits since it was parsed).
  - `update`: small pending edits (≤ `INLINE_EDITS` changes touching ≤ `INLINE_BYTES`) are re-parsed incrementally on the UI thread, stopping after `INLINE_TIME` (8 ms: with the highlight query and the frame a key stays near 10 ms); anything else (first parse, big edits, a re-parse that ran out of time) returns a `ParseJob` (rope snapshot + the edited old tree) for `spawn_blocking`; `ParseJob::run` is blocking and returns `Parsed` (dropped by `parsed` unless its generation is current; a tree finished after its cancel is freed in the job, not on the UI thread).
  - `parse` reads the rope chunk by chunk (`pos::chunk_from`, no copy). A stop (deadline or cancel) is checked in both the progress callback and the read callback (one lexer step can scan to the end of the file, e.g. an unterminated `/*`); once stopped it reports end of text and the result is dropped.
- `highlight.rs` — `KEYS` (the theme keys a capture can map to; each is in `Theme::dark_plus`), `highlight_for(capture)` (the dotted name, else its longest prefix in `KEYS`: `function.method` → `function`; none → uncoloured), `Span { start, end, highlight }` (`ByteIdx` range; `Highlight::index()` indexes `KEYS`). Each language's query is compiled once (`OnceLock`; `warm` is called by `ParseJob::run`, so the UI thread never compiles it). `compute(language, tree, rope, start, end)`: a `QueryCursor` over the byte range (text predicates read the rope via `pos::bytes_in`), captures painted into a byte array (outer nodes first, inner over them; for the same node the later pattern wins), run-length encoded into sorted, non-overlapping spans clipped to the range (a block comment opened above the range colours its part).
  - `Highlights` (inside `Syntax`, reached through `Syntax::spans(rope, lines)`): up to 4 cached `Region`s (a byte range + spans + the `tree_version` they came from). With a current tree: a region of that version covering the lines, else query the lines ± `MARGIN` (50) and cache it (older versions dropped). Bytes are capped so one query stays under ~7 ms (~0.3 ms per KB of dense C++): only `MAX_QUERY_BYTES` (16 KB) from the first requested line's start are coloured (a 1 MB minified line: just its start, as VS Code stops tokenizing long lines), and the margin is at most `MARGIN_BYTES` (4 KB) either side; a caller wanting more (the Minimap) asks in pieces. Without one (re-parse running): the newest region that covers or overlaps, mapped through every change set by `Syntax::map_highlights` (from `Buffer::apply`; span starts `Assoc::After`, ends `Before`, so text typed at a span's edge stays plain until the new tree; emptied spans dropped). Positions are only compared, never used to index the rope. `set_language` and going `TooLarge` clear the cache. `tree_version` is bumped whenever a new current tree is installed (inline re-parse, or a background result with no edits queued).
  - Tests (in `highlight.rs`): prefix mapping, exact spans for C / C++ / Python snippets, `#match?` predicates (also on a node spanning rope chunks), a comment opened above the range, the cache (`highlight_queries_run()` counts misses: none when nothing changed; stale spans shifted by an insert; right after the re-parse), stale span edges, deleted spans, language change and the size limit dropping the cache, the long-line cap.
- `tokens.rs` — `Tokens`: a `TreeCursor` walk over the tree's leaves for positions asked in increasing order (each node stepped over once; an earlier position restarts from the root): `leaf_from(b)` (first leaf ending after `b`; zero-width missing leaves skipped), `leaf_at(b)` (the leaf holding `b`, `None` between tokens), `is_token(b, text)` (a bracket that isn't inside a string / comment: those are single leaves or content leaves), `each_leaf(lo, hi, f)`. Avoids `descendant_for_byte_range` per position, which scans a node's children linearly (a root with 60k children).
- Logging under `red::syntax`: parse times at debug, `slow parse` warning over 500 ms.
- Tests (`tests.rs`) drive `Syntax` through a `Buffer` without the app: `update` → `job.run()` → `parsed`; the random-edit test compares the incrementally kept tree with a fresh parse (S-expression and every node's range and positions); `input_edits_match_a_reference` checks the `InputEdit`s against ones computed by applying each change to a string. tree-sitter's error recovery can differ between incremental and fresh parses after many broken edits, so it runs a fixed number of seeded steps.
