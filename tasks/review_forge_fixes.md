Bugs and adapter differences found by reading the forge layer and the review code (16 Nov 2026, at `505f712`). Nothing here was checked against a live server: each subtask first checks the forge's documented behaviour (the official API docs, or a self-hosted server's own `/swagger.v1.json` for Gitea) and records what it found under "Forge differences" in [mr_review](mr_review.md), then fixes. Five independent subtasks, one commit each.

  - Needs: the forge layer (`jed/src/forge/mod.rs` `Forge` trait and types, `gitea.rs`, `github.rs`, `gitlab.rs`, `http.rs`, `fake.rs`), suggestions (`jed/src/suggestion.rs`, `jed/src/app/review_suggest.rs`), the review model and lookup (`jed/src/review.rs`), writes (`jed/src/review_write.rs`, `jed/src/app/review_write.rs`), the composer and drafts (`jed/src/app/review_comment.rs`, `jed/src/review_drafts.rs`), thread tabs (`diff_view::ThreadTab`, `app/review.rs` `open_thread_tab`), `git::range` (`changes`, `local_info`)
  - Rules for every subtask: tests in `jed/src/review_forge_fixes_tests.rs` (a `//!` doc, a `#[cfg(test)] mod` line in `main.rs`), named `review_forge_fixes_*`; unit tests in the module's `mod tests`. Adapters are tested against `forge::fake`, never a real server. Docs kept in step (`docs/forges.md`, `docs/dev/conventions.md`'s Forges section, the nested CLAUDE.md line). No real hostnames. A behaviour that the docs don't settle is written down as "unverified" with the hand check that would settle it, not guessed silently.
  - Done when:
    - on GitLab, a plain ` ```suggestion ` fence in a multi-line comment replaces only the comment's last line when applied, `suggestion:-N+M` its range; on GitHub and Gitea a plain fence still replaces the whole anchored range; a multi-line suggestion edited or replied from jed on GitLab means the same on GitLab's page as in jed
    - Submit Review (Request Changes) with no drafts is accepted by the Gitea fake under the rule the real server applies (a body is sent when one is required)
    - a merge request from a fork's branch of the same name is treated the same way on Gitea, GitHub and GitLab (found or not found on all three, as the subtask decides), and `MergeRequest::head_repo` is filled on all three
    - Insert Suggestion in a thread tab's reply box fences the thread's anchored lines (or is refused with a message that says why)
    - on GitHub, a draft on a line the merge request's diff doesn't cover is held back and named in PENDING before the submit, and the other drafts are posted
    - a reviewer who asked for changes on GitLab shows in the approval line; a dismissed approval doesn't bring back the same reviewer's older verdict
    - `scripts/check` is green
  - Subtasks (one agent and one commit each):
    - review_forge_fixes-a: suggestions mean what the forge means
        - Today `suggestion::parse(body, anchor)` reads a plain fence as "replace the anchored lines" for every forge (`jed/src/suggestion.rs:106`). GitLab reads a plain fence as `-0+0`: the comment's last line only. `gitlab::gitlab_body` (`jed/src/forge/gitlab.rs:394`) already rewrites a plain fence to `suggestion:-N+0` at submit for that reason, but only `submit_review` calls it: `edit_comment` and `reply` post the plain fence.
        - First check GitLab's suggestion docs (the `-N+M` syntax, the plain fence's meaning, limits) and record them in mr_review.md's GitLab bullet, which today says "unverified".
        - Fix on read, in the GitLab adapter: normalise each comment body's plain suggestion fences to `suggestion:-0+0` as it is read (`gitlab::comment`), so `parse` needs no forge argument and everything downstream (blocks, Apply, Claude's tool) agrees. Or give `parse` the `forge::Kind`: pick whichever leaves the text the user sees when editing their own comment closest to what GitLab stores, and say which in the report.
        - Fix on write: `edit_comment` and `reply` run the body through the same rewrite as `submit_review`. They need the thread's line span: `edit_comment` already gets `range`; `reply` gets the thread id only, so either the trait's `reply` takes an optional span or the app rewrites before calling (the app knows the thread's anchor). A reply's suggestion applies to the thread's anchor, as today.
        - The Apply button's visibility (`app/review.rs` `sync_review_threads`, `conv_spot`) and `apply_suggestion_of` use the same reading.
        - Tests: `parse` / the adapter on a GitLab multi-line thread with a plain fence (one line), with `-2+0` (three lines), GitHub's plain fence on a range (whole range); the fake GitLab receives the rewritten body on edit and on reply; an applied GitLab plain-fence suggestion changes one line (driven through the app).
    - review_forge_fixes-b: verdicts — Gitea's empty body, dismissed reviews, GitLab's changes requested
        - Gitea: jed always sends an empty review body (`app/review_write.rs:175`); `github.rs:462` substitutes "Review comments" / "Changes requested", `gitea.rs` doesn't. Check Gitea's rule for `POST /pulls/{n}/reviews` (which events need a body, and whether comments count as one) in its swagger and source, then apply the same fallback there; move the fallback text to one place (`forge/mod.rs`) that both adapters call. Make the Gitea fake refuse what the real server refuses.
        - Dismissed reviews: `forge::latest_approvals` skips a `None` verdict, so on Gitea (dismissed reviews filtered out before the fold, `gitea.rs:362`) and GitHub (`DISMISSED` maps to `None`) a reviewer's dismissed approval brings back their older "changes requested". A dismissed review clears that reviewer's earlier verdict: give the fold a third input (`Verdict::{Set(state), Keep, Clear}` or similar) and map dismissed to `Clear`. Decide and document what Gitea's `stale` flag does (an approval made before a later push): shown as approved today.
        - GitLab: `approvals` reads only `…/approvals` `approved_by`, so a reviewer jed itself marked `requested_changes` never shows. Check the docs for where the reviewer state is readable (the merge request's reviewers endpoint and its `state` values, and from which GitLab version), read it in `comments()` and add `ChangesRequested` entries; a server without it (404) shows approvals only, logged once.
        - GitLab: `comments()` calls `merge_request()` again only for the head sha and URL; pass them in from the lookup or cache per call so a lookup does one request fewer. Sort GitLab's conversation by `created_at` as the other two do.
        - Tests: each adapter against the fake (a dismissed approval after changes requested shows nothing for that reviewer; GitLab changes requested shown; the Gitea Request Changes body); the panel's approval line.
    - review_forge_fixes-c: fork merge requests matched the same way
        - Today GitHub asks for `head={base owner}:{branch}` (`github.rs:346`), so a fork's pull request is never found, and its doc comment says the opposite. Gitea (`gitea.rs:304`) and GitLab (`gitlab.rs:413`) match the branch name only, so a fork's merge request from a branch of the same name (`main`, `patch-1`) is shown as the checked-out branch's. `MergeRequest::head_repo` is filled by Gitea and GitHub, never by GitLab (`source_project_id` needs a lookup, or the list's `references` / `source_project_id` compared with the project's id), and nothing reads it.
        - Rule: `find_open` returns the open merge requests whose head branch is `head_branch` **in the repository asked for** (`head_repo` equals `repo.path`, case-insensitively, or is unknown). Fill `head_repo` on GitLab (compare `source_project_id` with `target_project_id`: equal means the same project; else leave the fork's path if the answer carries it). Fix the GitHub doc comment. [review_find_mr](review_find_mr.md) builds on this to find a fork's merge request from the fork's clone.
        - Tests: each adapter's fake serves a same-repository and a fork merge request on the same branch name; only the first is returned.
    - review_forge_fixes-d: drafts and suggestions in the wrong place
        - Insert Suggestion in a thread tab: `compose_in` (`app/review_write.rs:334`) gives a thread tab's reply box the anchor's own line numbers, and `review_insert_suggestion` (`app/review_suggest.rs:253`) indexes the tab's doc with them. The doc there is the snippet (a few lines, numbered from `ThreadTab::base`), so it says "The diff is updating, try again" or fences the wrong lines. Read the lines through the tab's base (`line - base`), or from `ThreadRow::code`; a thread with no code refuses with "This thread's code isn't available".
        - GitHub and lines outside the diff: a review is one atomic request, and GitHub refuses a comment on a line outside the diff's hunks (their context lines included), which fails every draft with the same error. jed's review diff shows the whole file, so any line can get a draft. Check the docs for exactly which lines are accepted (hunk lines and context; whether `subject_type: file` is an alternative). Then hold such a draft back before the submit, as a draft on a changed line is held back today (`Drafts::drift` / `DraftRow::held`, PENDING names it: "not in the merge request's diff"): compute the merge request's hunk ranges from the local diff of merge base to `mr.head.sha` (`git::range`), per file and side, in `review_drafts::check` (off-thread already). Apply it on GitHub only unless the docs say Gitea or GitLab refuse the same (GitLab's known gap about context lines needing both `old_line` and `new_line` is in mr_review.md: fix it here if the docs confirm it, since the same hunk data gives the other side's line number).
        - The composer says so when opened on such a line on GitHub (a note in the box's header), so the user learns before writing.
        - Tests: a thread tab's reply box inserts the anchored lines; with the GitHub fake, a draft outside the hunks is held back and named, the others post; with Gitea it posts.
    - review_forge_fixes-e: small differences and stale text
        - Token: `Client::new` allows no token ("a public repository may answer without one") but `review::lookup` returns `Empty::NoToken` first (`review.rs:178`). Pick one: keep requiring a token (writes need it; say so in `http.rs`'s doc), or let a tokenless lookup read and refuse writes with "No token". Make the docs and both comments agree.
        - GitHub: log (Review tool log, once per lookup) when the GraphQL page cap (`MAX_GRAPHQL_PAGES`) or a thread's 100-comment cut drops something, as the blob-id cap does; page a thread's comments past 100 if that is simple. Read `startDiffSide` and treat a range whose ends are on different sides as anchored on its end line only.
        - Polling: mr_review.md says the 60 s refresh runs "while the view or a review tab is visible"; `review_visible()` (`app/review.rs:42`) checks the panel only. Make it true (a review diff or thread tab active in any group counts), with a `next_timer` test.
        - Stale text: `gitlab.rs:506` ("Drafts the user has made on GitLab's own page are published too" — the code refuses instead); `forge/mod.rs:288` ("Writes … are added by the review-writing subtask"); `app/review_comment.rs:12` ("Submit Review (later)"); `kind = "forgejo"` is accepted (`forge/mod.rs:41`) but `docs/forges.md`, `config.rs`'s doc and its error text list only three kinds.
        - Then run the task's done-when, fill in "What it changed", "Deferred" and "Still to check by hand" (per forge, on a throwaway merge request), and mark the task ✅.
