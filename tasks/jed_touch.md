jed's version of [jmux_touch](jmux_touch.md). It pads every group's tab bar (editor groups and the terminal area's) so a finger can hit a tab, its `×` and the scroll arrows. A touch screen is usually a small one too, so the layout also gives the editor the width: the side panel floats over the editor and gets out of the way once it has opened something, the bottom panel likewise, editor groups are never side by side, and lines wrap. A finger can't right-click or drag-to-scroll, so a swipe scrolls and a hold stands in for the right button. jed has no attach, so the layout is chosen when jed starts: `--touch` on the command line, or `touch_layout = true` in `settings.toml` for a machine that always has a touch screen. The setting applies on Reload Settings.

  - Needs: `jmux_touch` (`jtui::tabs::TabMetrics`, `NORMAL` / `TOUCH`, and the rules for which rows and cells a tap hits); `jmux_touch_gestures` (`jtui::touch`: swipe scrolls, tap acts on release, hold lifts a tab, so jed's bars behave the same); each subtask lists the code it touches.
  - The switch (subtask a): `--touch` sets it for this run and wins over the setting. A file opened through the socket into a running jed doesn't change it. `touch_layout` (bool, default `false`) in `[settings]`, with no per-language override. Everything below is read through one `App::touch()`; with neither set nothing changes.

Do the same as jmux: 3 rows with the label on the middle one; 2 cells of padding at each end and around `×` (or `●` on an unsaved tab; jed's bar has no hover); a 3-cell close target; 3-cell `‹` / `›`; the 3-cell `+` at the bar's right end (`TabMetrics::new_tab`) opening a tab in that group; the drop marker on all 3 rows. The group number sits on the label row. The bar's height comes from one function used by the frame and by whatever sizes editors and shells, so a shell's PTY size, an editor's visible lines and the scroll bars agree with what's drawn.

A swipe on a bar scrolls its tabs, a tap acts on release and a hold lifts a tab, through `jtui::touch` as jmux's bars do. The tab tooltip (`ui/tab_tip.rs`) is placed below or above the taller bar.

    - jed_touch-b: gestures in text and shells — swipe to scroll, tap, hold then drag to select, hold for the context menu
      - Needs: `jtui::touch` (`Press`, `Gesture`: its `Swipe` carries only `dx`, so it gains `dy`, with jmux's bars reading `dx` as now), the editor's and shell's mouse handling (`app/mouse.rs`: text drag-select, wheel scrolling, double / triple click, the shell's mouse reporting), the diff and hex views' mouse handling, the context menus (`file_info`) and the right-click actions without one (explorer File History)
      - Swipe to scroll: in the touch layout a press in an editor's text, a diff or hex view, or a shell runs through `jtui::touch::Press` instead of starting a selection. A tap places the cursor (or clicks, in a shell that reports the mouse); a swipe scrolls the view by the rows and columns moved, as the wheel does (a shell's scrollback, or wheel events to a program that reports the mouse); a hold then drag selects from the press, as a mouse drag does today, and the release ends it. Double- and triple-tap select a word and a line as clicks do. The scroll bars still drag as before.
      - Hold for the context menu: in the touch layout a hold that ends without moving opens the context menu the right button would at that spot (the editor's, a tab's, an explorer row's), or runs what right-click runs where there's no menu. On a tab bar the hold still lifts the tab: the menu opens if it's released without moving.
      - Done when: a swipe in an editor, a diff, a hex view and a shell scrolls it without selecting, a tap moves the cursor, a hold then drag selects, double- and triple-tap select a word and a line; a hold opens the context menu on the editor, an explorer row and a tab (released without moving); with the layout off, presses behave as today.
      - Tests: `jed_touch_b_*` in `jed/src/jed_touch_tests.rs`: swipe, tap and hold-drag in an editor and a shell (including one that reports the mouse), a diff and a hex view; the hold menus; `jtui::touch` unit tests for `dy`.

    - jed_touch-c: room for the editor — the side panel floats and hides after an open, the bottom panel hides after a jump, side-by-side groups merge, lines wrap
      - Needs: the side panel's drawing and layout (`ui/mod.rs`, `layout.rs`) and its views that open tabs (explorer, Source Control, search results, Git History, Tools), `ToggleSidebar`; the bottom panel (`PanelTab::Problems`, `Locations`); `jtui::split::SplitTree` / `SplitDir`, `SplitRight`, `close_group` (`app/files.rs`), tab drop on an edge, the session restore; `word_wrap` in `settings.rs`
      - Side panel over the editor: in the touch layout the side panel is drawn over the editor area's left edge instead of beside it, so showing or hiding it doesn't resize editors or shells (no PTY resize, no reflow). It has a border on its right edge; a tap in the editor area outside it hides it (the tap isn't passed on). Its width is the same setting as now, capped so at least 20 columns of editor stay visible.
      - Side panel auto-hide: in the touch layout, an action in the side panel that opens or shows a tab in an editor group (a tap or Enter on an explorer file, a Source Control change's diff, a search result, a Git History commit or file, a tool's log) hides the side panel the same way `ToggleSidebar` does, and focus goes to the editor. The width and the view are kept, so the activity bar or `ToggleSidebar` brings it back as it was. Actions that open nothing (expanding a folder, staging, a context menu, a rename) leave it shown, as does opening from the palette, Quick Open or the keyboard outside the panel.
      - Bottom panel auto-hide: in the touch layout, going to a problem or a location from the bottom panel (tap or Enter) hides the panel as its toggle does, focus going to the editor; the panel keeps its tab and height. A task run's tab doesn't hide it.
      - Side-by-side groups merge: in the touch layout the editor area has no `SplitDir::Right` splits. On start-up (after the session restores), and when Reload Settings turns the layout on, each `Right` split's groups merge into one: the right-hand group's tabs are appended to the left-hand one's in order, a buffer shown in both keeps the one view (the focused group's, else the left's, selections and scroll), the focused tab stays active, and the other group closes through the usual path. `Down` splits stay. While the layout is on, the commands and drops that would split right split down instead: "Split Editor Right", Cmd+N one past the last group, and a tab dropped on a group's left or right edge (the drop marker shows the bottom half). The splits aren't restored when the layout turns off, and the session saves the merged layout. The terminal area's splits are left alone.
      - Wrap: in the touch layout `word_wrap` defaults to `on`; a `word_wrap` set in `settings.toml` (global or per language) still wins.
      - Done when: showing the side panel leaves editors' and shells' sizes unchanged and a tap beside it hides it; opening a file, diff or result from the side panel hides it and the activity bar brings it back at the same width and view, while expanding a folder or staging leaves it shown; going to a problem or a location hides the bottom panel; a session with side-by-side groups starts as one group holding all their tabs (stacked splits kept), Split Editor Right and an edge drop on the left or right split down, and Reload Settings turning the layout on merges the same way; lines wrap unless `word_wrap` is set; with the layout off nothing changes.
