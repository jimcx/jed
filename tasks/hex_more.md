See [Binary files (hex view)](../PLAN.md#binary-files-hex-view) and [tasks/hex.md](hex.md) (its notes for later tasks). Two of that section's "Deferred" items: files over 256 MB (paged reads) and a data inspector.

  - Large files: a hex tab no longer holds the whole file. `HexDoc`'s `Arc<[u8]>` becomes a paged source: fixed-size pages (e.g. 64 KiB) read with positioned reads (`FileExt::read_at` on one open `File` per doc) into an LRU cache with a byte cap (e.g. 64 MiB, shared by the tab's splits), keyed by the doc's `Stamp` so pages from two versions of the file never mix. A file small enough (e.g. ≤ 8 MiB) is still read whole at open, as one resident chunk behind the same interface, so small files look exactly as today. `HEX_MAX_BYTES` and `check_size` go: any size opens, including files over 4 GiB (offsets become `u64`; the offset column widens past 8 digits as the module doc's "one deviation" already describes)
    - Never block the UI thread: a frame asks the cache for its visible rows; a missing page draws its bytes as a placeholder (`hexEditor.pending` theme key, e.g. `··` / `·`) and queues a read; reads run in `spawn_blocking` (a few pages per job, the visible ones first, then one screen above and below as prefetch) and report with `AppEvent::View(ViewEvent::HexPages { id, stamp, pages })`; stale ones (other stamp, tab gone) are dropped. A page that fails to read (file truncated under us) draws as unreadable and is retried after the next disk check, not every frame. No `mmap`: a file truncated by another process turns reads into SIGBUS, and page faults would block the UI thread anyway
    - Find: the hex find model moves to streaming over the source — `find_next` / `find_prev` read chunks (overlapping by `query.len() − 1`) off the UI thread for a paged doc, with a generation so a newer query or keystroke cancels the old one (the widget shows "…" meanwhile, and the cursor moves when the result arrives); highlights stay the visible window's own search, over loaded pages only (a match touching a pending page is highlighted when it loads). `count` streams too, and becomes cancellable (hex's "Deferred": cancelling a stale whole-file count). A resident doc may keep today's UI-thread search
    - Copy: a selection up to a cap (e.g. 16 MiB of bytes, so ~48 MiB of hex text) is read off-thread and copied when it arrives; past the cap a message says how big the selection is and nothing is copied. Seeding find from a selection keeps its 256-byte limit (read from cached pages, else not seeded)
    - Disk changes: a changed stamp drops the cache (no whole-file re-read); the length is re-taken from the metadata and the cursor / top clamped as today; `(deleted)` as today. Sessions and navigation are unchanged (path, cursor, column, top — now `u64`, serde reads older files)
    - Status bar: size shown as `1.2 GB (1288490188 bytes)` for big files; offsets as today, wider
  - Data inspector: a panel in the hex tab showing the bytes at the cursor as typed values — toggled by "Hex: Toggle Data Inspector" (`hex.toggleInspector`, palette, unbound; remembered per session like the find toggles, on by default), drawn to the right of the rows when the tab is wide enough for 8-byte rows plus the panel, else under them (the row layout fits the width left over). Rows (label, value), from the cursor's byte, each blank (`—`) when it would run past the end of the file:
    - `binary` (the byte as 8 bits), `i8` / `u8`, `char` (the byte as ASCII, or `\x7f`-style escape),
    - `i16` / `u16` (short), `i32` / `u32` (int), `i64` / `u64` (long), `f32` / `f64` (float / double, `NaN` / `inf` as Rust prints them),
    - `UTF-8` (the code point starting at the cursor, `U+00E9 é`, or `invalid`), `UTF-16` (the code unit pair as a code point in the current byte order)
    - Labels use both names where C's differ from Rust's (`i16 short`, `i32 int`, `i64 long`), so they read either way
  - Byte order: "Hex: Toggle Byte Order" (`hex.toggleEndianness`, palette; bound on a hex tab only — pick a free key in `Context::Hex`, e.g. Alt+E, and check `docs/terminals/README.md` if it's a Cmd binding) flips the inspector between little-endian (default) and big-endian; the panel's header shows `LE` / `BE` and a click on it toggles too; the choice is per session (`App` state, saved in the session like the find toggles), not per tab. A `hex_byte_order` setting (`"little"` / `"big"`) sets the starting order
  - With a selection: the inspector reads from the selection's start instead of the cursor, and the row whose width equals the selection's length (1 / 2 / 4 / 8 bytes) is highlighted; the bytes a highlighted row covers are outlined in both columns (`hexEditor.inspected`), so it's clear which bytes a value comes from. "Hex: Copy Value" copies a clicked / highlighted row's value text
  - Grouping: a `hex_group_bytes` setting (1 / 2 / 4 / 8, default 1 = today's `hexdump -C` look) and "Hex: Cycle Byte Grouping" (`hex.cycleGrouping`, palette) group the hex column into words, `xxd -g` style: each group's digits run together with one space between groups (the extra space every 8 bytes stays). In little-endian order each group's bytes print reversed, as `xxd -e` does (so a u32 reads as its value); big-endian prints them in file order. Rows stay a power of two bytes wide and a multiple of the group (`Layout::fit` takes the group); the cursor and selection still move by byte, and a byte's cell is its two digits inside its group (clicks hit them through `Layout::hit`); the ASCII column never reorders. The grouping is per session like the byte order; Copy of hex text follows the grouping as shown
  - Follow pointer: "Hex: Follow Pointer" (`hex.followPointer`, palette; bound on a hex tab to a free key in `Context::Hex`) reads a u32 at the cursor (a u64 when the selection is 8 bytes, or the inspector's highlighted row is 64-bit) in the current byte order and moves the cursor to that offset, recording the jump for back / forward (navigation within the tab: a hex entry with its offset, where hex-d recorded path only) so Ctrl+- returns; an offset past the end is a message, nothing moves. The inspector's integer rows offer it on click too (a `→` beside the value)
  - Copy as: "Hex: Copy As…" (`hex.copyAs`, palette) opens a quick pick of formats for the selection (else the cursor's byte): hex without spaces (`7f454c46`), hex with spaces (today's Cmd+C), C array (`{ 0x7f, 0x45, 0x4c, 0x46 }`, 16 per line), Rust array (`[0x7f, 0x45, …]`), Python bytes (`b'\x7fELF'`, printable ASCII as itself), base64, and the selection as a single value (its inspector row, when 1 / 2 / 4 / 8 bytes). Formatting is pure functions in `hex.rs` (unit tests per format: empty, one byte, quotes and backslashes in Python, base64 padding); the same size cap and off-thread read as Cmd+C
  - Needs: `hex.rs` (`HexDoc`, `HexTab`, `Layout`, find), `app/hex.rs`, `ui/hex.rs`, `ui/status.rs`'s `hex_status`, the find widget's count / next plumbing (`ViewEvent::HexCount`), `Context::Hex` keymap, sessions (`TabState::Hex`), settings (`edit::Settings`, doc table, `TEMPLATE`)
  - Done when: a 6 GiB sparse file (`set_len`, a few marker bytes written near 0, 4 GiB and the end) opens at once as a hex tab with 9-digit offsets, the process's memory stays under ~100 MB while scrolling end to end with Cmd+Down / Cmd+Up and paging, the markers show at their offsets, Ctrl+G to a marker past 4 GiB lands on it, Cmd+F finds a marker (next / previous across the 4 GiB boundary) without a frame over 16 ms (`SLOW_FRAME` never logged), the count arrives and a new query cancels the old count; a file truncated on disk while open clamps the cursor and draws no stale bytes; copying a selection over the cap gives the message; a ≤ 8 MiB file behaves exactly as before (the `hex_*` tests pass unchanged except where the size limit is gone). The inspector on bytes `01 02 03 04 05 06 07 08` at offset 0 shows `u16 513`, `u32 67305985`, `u64 578437695752307201` little-endian and `258`, `16909060`, `72623859790382856` after the toggle; `00 00 80 3f` shows `f32 1` LE, `00 00 00 00 00 00 f0 3f` shows `f64 1`; a 4-byte selection highlights the `i32` / `u32` rows and outlines those bytes; three bytes before the end shows `—` for 32 / 64-bit rows; the toggle, byte order and grouping survive quit and reopen. Grouping 4 on `01 02 03 04` shows `04030201` little-endian and `01020304` big-endian, rows stay aligned, and a click on the `02` digits puts the cursor on offset 1; with `10 00 00 00` at offset 0 and a 0x20-byte file, Follow Pointer moves to 0x10 and back / forward returns to 0, and `ff ff ff ff` gives the past-the-end message; Copy As on `7f 45 4c 46` gives `7f454c46`, `{ 0x7f, 0x45, 0x4c, 0x46 }`, `[0x7f, 0x45, 0x4c, 0x46]`, `b'\x7fELF'` and `f0VMRg==`
