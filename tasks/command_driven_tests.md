id: command_driven_tests
name: Command-driven tests
summary: jed's and jmux's tests run features through their `Command` instead of pressing platform keys; one light suite per app checks that every default key reaches its command, on each platform
status: in-progress
priority: 0
dependencies: []
---

Tests keep breaking on one platform because they press keys that only one platform binds. jed's test files make about 2700 `app.press(..)` calls; about 920 of them use Ctrl, Cmd or Alt. 33 files define a local `cmd()` (SUPER on macOS, CONTROL elsewhere). That helper fails when macOS binds a different key, not just a different modifier: Ctrl+Home on Linux is Cmd+Up on macOS, and Ctrl+A selects all on Linux but goes to the line's start on macOS. Each failure has been fixed one by one, leaving 97 `cfg!(target_os = "macos")` branches in the test files and a run of "fix tests on macOS / Linux" commits. Most of these tests are about what a feature does, not which key starts it. They should run the command (`App::test_execute`, already used about 900 times), and the keys should be checked once, in one place.

  - Needs: the test helpers in `app/mod.rs` (`#[cfg(test)] impl App`: `press`, `test_execute`, `press_file_start` / `press_file_end`), `config/keymap.rs` (`Keymap`, `defaults(platform)`, `Platform`, the existing per-platform tests), `jtui::keymap` (`lookup`, `binding_for`, `KeyCombo`), the key dispatch in `App::handle_event` (`app/mod.rs`, the overlay chain then `keymap.lookup(&key, self.context())`), `app/field.rs` (`has_field_meaning`), `terminal_copy_key`, `is_shell_key`, and jmux's `command()` test helper (`505f712`), which does the same thing
  - Helpers (`#[cfg(test)] impl App`):
    - `test_execute(cmd)` stays the default way to run a command in a test. Don't rename it (`App::run` is the event loop)
    - `press_bound(cmd)`: presses the key this platform's keymap binds to `cmd` *in the current context*. It picks, from all of `cmd`'s bindings, one that `keymap.lookup(.., self.context())` resolves to `cmd`. When none does, it panics with the command, the context and the keys it tried. Use it in tests where key handling is what's being tested (a focused field, a shell tab, an overlay), never just to start a feature
    - `press_file_start` / `press_file_end` become `press_bound` of their commands, or are removed if all their callers switch to `test_execute`
    - a test-only "record, don't run" switch on `App` (e.g. `test_dispatch_log: Option<Vec<Command>>`): while it is set, the keymap branch of `handle_event` pushes the command it found instead of calling `execute`. Nothing else in the dispatch changes
  - Key routing suite (`jed/src/command_driven_tests.rs`):
    - keymap level, both platforms in one run (`Keymap::default_for(Platform::MacOs / Linux)`): every default binding's key resolves to its command in its context (`lookup`); the default list has no two entries for one (key, context) with different commands (a later one would silently replace the earlier); every command a test file reaches through `press_bound` has a binding on both platforms. Skip any check `config/keymap.rs` already makes
    - app level, current platform: for each `Context` that can be set up headlessly (editor, find, replace, palette, a focused field, the explorer, search, a shell tab, a diff tab, a hex tab, the review panel, ...), build the app in that context, turn on the record switch, press each binding that applies there (its own, its parents' and the global ones, minus the ones `passes_through` or `has_field_meaning` gives away), and check that the log is exactly the bound commands in order. Since nothing runs, one app per context covers all its bindings. A context that can't be set up is listed in the file's `//!` doc with the reason
    - the dispatch's special cases, each a normal (running) test pressing real keys: an open prompt, context menu, cheat sheet, keyboard shortcuts view, peek and inline rename take a bound key before the keymap; a focused field keeps Ctrl/Cmd+A, C, V, X, Z (`has_field_meaning`); a shell tab gets plain Ctrl+letters except Ctrl+Q (`is_shell_key`); Cmd+C over a terminal selection copies on macOS and Ctrl+C stays SIGINT on Linux (`terminal_copy_key`). Use `cfg!(target_os)` only where the behaviour itself differs by platform
  - Migration: every test that presses a Ctrl, Cmd or Alt key to start a feature calls `test_execute(Command::..)` instead. Tests that really are about a key use `press_bound`, or move into the routing suite if it already covers them. The local `cmd()` / `primary` / `ctrl()` helpers are deleted, along with every `cfg!(target_os = "macos")` branch that only chose a key. Plain keys (Enter, Esc, arrows, Tab, Backspace, typed text; about 1770 presses) stay as `press` / `type_text`. A script can propose the command for each press by looking the key up in `Keymap::default_for(Platform::Linux)` in the test's context. Check each one by hand: a press inside a field, palette or shell is often about the key
    - mod.rs-level tests outside `*_tests.rs` (`app/disk.rs`, `app/palette.rs`, `mr_review_tests/`) are included
    - the guard: a test in `command_driven_tests.rs` reads every `.rs` under `jed/src` and fails on a `.press(` whose modifiers include CONTROL, SUPER or ALT outside an allowlist (`command_driven_tests.rs` itself, plus any file and line given a reason in the allowlist). Its message points to `test_execute` / `press_bound`
  - Docs: the rule for new tests is **run the command, don't press its key**: a test starts a feature with `test_execute(Command::..)` (jmux: `run(Command::..)`). It presses a Ctrl, Cmd or Alt key only when the test is about key handling, and then through `press_bound`, never a raw platform key. Write it in each place an agent reads before writing a test:

  - jmux: its tests have the same problem on a smaller scale.
