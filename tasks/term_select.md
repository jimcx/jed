---
id: term_select
name: Mouse selection in the terminal
summary: the complement of `term_mouse` — when the program inside a shell or task tab has *not* asked for the mouse, a left-drag over its screen selects text, drawn highlighted, and Cmd/Ctrl+C copies it
status: done
priority: 0
dependencies: []
---

  - The model (`tasks/select.rs`, `term_select-a`): a `Selection { anchor, head }` of `(row, col)` cells in the screen's visible-viewport coordinates (the space `vt100::Screen::cell` / `contents_between` use, scrollback folded in), the head's column exclusive so a click selects nothing; `Selection::rows()` normalises anchor→head for copy and drawing; `copy_text(screen, selection)` is `contents_between` over that range with trailing spaces trimmed per line (soft-wrapped rows joined); `top_row(screen, height)` moves here from `ui/task.rs` so the mouse, drawing and copy share one definition
  - The wiring (`term_select-b`): `Run`'s `Shared` gains `selection: Mutex<Option<Selection>>` with `selection` / `set_selection` / `clear_selection` / `copy_selection`, cleared by a resize and new output (the visible rows shift; a scroll used to clear it too until `term_select_scrollback` made it move with its text). `Drag::Terminal` and `terminal_select` in `app/mouse.rs` seed / extend the selection on a left-drag over a shell (`Hit::Editor`) or task (`Hit::Panel`) whose program isn't reporting the mouse (`screen_cell` maps the pointer to a screen cell through `top_row`, clamped); a click clears it, the wheel still scrolls the scrollback, and a program that has asked for the mouse keeps every event (`term_mouse`), so `vim` / `tmux` / `htop` are unchanged. `draw_screen` paints the selection's rows with `editor.selection`'s background over the terminal colours (drawn rows only). Cmd/Ctrl+C copies the active terminal's selection (a shell tab with the editor's keys, else the shown task) through `Clipboard::write`
  - Also: Cmd/Ctrl+C over a terminal is key-routed (`terminal_copy_key`) — the editor's copy key with a selection copies, without one it falls through to the program (Ctrl+C is SIGINT), and a rebind follows; `active_terminal` is focus-gated so a task's lingering selection can't hijack an editor's own copy
  - Deferred: keyboard selection and select-all, Shift+drag to select while the program captures the mouse, auto-scrolling while a drag leaves the edge, and a `terminal.selection` theme key of its own (reuses the editor's for now)
  - Tests: `tasks::select` unit tests (normalisation both ways, per-line trailing-space trim, wrapped rows, the scrolled-back viewport, `top_row`); `term_select_tests.rs` end to end — shell and task drag/highlight/copy with trailing-space trim, an ended run drawn from `top_row` (the drag's cells map to `top + row`), a click clears and copy leaves the clipboard alone, a mouse-reporting program keeps every event and selects nothing, and new output / the wheel clear the selection
  - Still to check by hand: a real mouse drag under a real terminal with wide / CJK glyphs and soft-wrapped lines, then Cmd+C into another app (system `arboard` / OSC 52 over SSH); a drag while output streams; dragging the panel border mid-drag (the resize clears); `vim` / `htop` / `tmux` with mouse reporting; a drag on a scrolled-back screen
  - Done when: over a shell and a task tab whose program hasn't asked for the mouse, a drag highlights the cells and Cmd/Ctrl+C copies exactly that text (trailing spaces trimmed); a click clears the highlight; with the mouse on (`\033[?1000h`) the program still gets every event and nothing is selected; new output and the wheel clear it; the model's unit tests cover the copy's normalisation, trailing-space trim and wrapped rows
