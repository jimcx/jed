---
id: history_stream
name: Streamed git history
summary: the Explorer's Git History and the Source Control view's commits pane show their first commits at once and fill in as a resumable walk goes on, instead of waiting for the whole history on every page
status: open
priority: 0
dependencies: [git_history, scm_branch_history]
---

Both history lists are paged (`git::log::PAGE`, 200), but every page still waits for a walk of the whole history, so in a big repository nothing shows for seconds and each later page waits again:

- **Branch history** (`git::log::branch`, `src/git/log.rs`): `revwalk.set_sorting(Sort::TIME)` makes libgit2 set `walk->limited` (`revwalk.c`'s `git_revwalk_sorting`: any sort mode). `prepare_walk` then runs `limit_list` over every reachable commit before `next()` yields the first. Each page opens a new revwalk and skips past what's already loaded, so the full walk happens on every page.
- **File history** (`git::log::commits` / `Walk::page`): the walk is ours and incremental, but a page returns only once it has found `skip + limit + 1` commits that touch the path, or the history ends. Most files have fewer than 200 commits, so the first page walks to the root, reading a tree path at every commit. A later page restarts at HEAD and re-walks the skipped commits.

The fix: a resumable walk that reports what it has found in pieces as it goes, kept alive while the list needs more, with libgit2's revwalk sort no longer used.

  - Needs: `src/git/log.rs` (`commits`, `branch`, `Walk`, `PAGE`), `src/git_history.rs` (`GitHistory`: `commits`, `more`, `loading`, `generation`, `stale`), `src/app/git_history.rs` (`sync_git_history`, `history_page`, `git_history_done`), `src/app/branch_history.rs` (`sync_branch_history`, `branch_page`, `branch_history_done`), `GitEvent::History` / `GitEvent::BranchHistory` (`app/git.rs`), `ui/side.rs`'s history rows ("Reading history…", the loading row). Read docs/dev/conventions.md's background-work rules and docs/dev/app.md's `git_history.rs` / `branch_history.rs` entries first.
  - Design:
    - `git::log::Walker`: owns the opened `Repository`, the date-ordered heap (`(time, Reverse(seq), Oid)`), the queued set and the path-entry cache, all of which `Walk` already has. It also takes an optional path: `None` shows every commit and walks every parent, which is `git log`'s order without a path and replaces the revwalk in `branch`. `Walker::step(budget) -> Step { found: Vec<Commit>, done: bool }` walks until it has found `budget` commits, a time slice runs out (`Instant`, ~50 ms) or the history ends. It's blocking (call from `spawn_blocking`) and `Send`.
    - One long-running `spawn_blocking` job per list generation. It holds the `Walker` and loops: step, then send the commits found so far as a chunk (`GitEvent::HistoryChunk { path, generation, commits, done }` and a branch counterpart, or one event with a target enum). A chunk goes out every ~200 ms while the walk is still finding nothing, and at once when it has found the commits the list asked for. The job stops when it is `PAGE` commits past what the list asked for and waits for a "want more" request (a `std::sync::mpsc` or `tokio::sync::watch` of the wanted count, sent by `sync_*` when the list is scrolled near its end). It ends when the walk is done, an error occurs, the generation's cancel flag is set (an `Arc<AtomicBool>` stored with the list and set when the path, HEAD or repository changes), or the request sender is dropped.
    - The app side: a chunk with the current generation appends to `commits`. The first chunk of a reload replaces the old rows, keeping the selection-by-id and top rules `git_history_done` / `branch_history_done` already have. `more` stays true until a `done` chunk arrives. `loading` means the walk is running and the list is waiting on it, and the rows show the loaded commits plus the "Reading history…" row at the bottom while it is set. An error chunk sets `error` as today.
    - Order and simplification stay exactly as now: the `git` CLI comparison tests in `git/log.rs` must pass unchanged, rewritten over `Walker` where they call `commits` / `branch`. Keep `commits(repo, path, skip, limit)` / `branch(...)` as thin wrappers over `Walker` only if tests or other callers still need them; otherwise remove them.
  - Done when:
    - In a test repository of 5,000 commits where the file under test is touched only by the first and the last commit, the Explorer section shows the newest commit before the walk reaches the root. A test drives the app, holds the walk back (a test hook or a small time slice), and sees a chunk arrive with `more` still true. The full list (2 commits) is then right, with `more` false.
    - Same for the branch pane: the first chunk arrives before the walk ends, and the full list matches `git log --format=%H` from HEAD, which already covers equal dates and merges.
    - Scrolling to the end of a 450-commit branch history continues the same walk: there's no second walk from HEAD, which a counter on `Walker` steps or a test hook shows. The rows match `git log` in order, with no duplicates or gaps.
    - Switching the active file mid-walk, or a commit made outside jed (HEAD moves), cancels the old job (its later chunks are dropped, and the job exits; a test sees the flag set and no more events) and starts a new one. The selection and top follow the existing rules.
    - A release budget test `milestone_history_stream_budget_first_chunk` (keeps `milestone` in its name, per CLAUDE.md) builds a 20,000-commit repository with `git fast-import`. It reports the time to the first chunk for the branch list and for a file touched once near HEAD, before and after the change, with a budget on the "after" numbers (aim for < 100 ms each in release).
    - `scripts/check` is green, and `git_history_tests` / `git/log.rs`'s tests pass with only the API changes they need.
  - Subtasks (one agent and one commit each):
    - history_stream-a: `git::log::Walker` (path or none, `step` with a found-commit budget and a time slice, resumable), `branch` / `commits` rebuilt on it or removed, the CLI comparison tests over `Walker` (pages taken by repeated `step`s match one full walk and `git log`), a unit test that a 5,000-commit walk's first `step` returns before the root is reached, and the release budget test's "before" numbers measured on the old code and recorded in this file
    - history_stream-b: the streaming jobs for both lists (cancel flag, want-more requests, chunk events, ~200 ms flushes), `GitHistory` / `sync_git_history` / `sync_branch_history` / `*_done` turned into chunk handlers, the loading row while the walk runs, the done-when app tests in `src/history_stream_tests.rs`, the budget test's "after" numbers, docs (docs/dev/app.md's `git_history.rs` / `branch_history.rs` entries, docs/dev/modules.md's `git::log` line)
  - Still to check by hand: in a large real repository (e.g. a clone of the Linux kernel or of rust-lang/rust), open a rarely changed file: its newest commits show at once, the loading row stays until the walk ends, and scrolling while it walks doesn't stutter. Open the Source Control view: its commits show at once. Switch files quickly while a walk runs: no stale rows, and one walk at a time (watch the CPU).
